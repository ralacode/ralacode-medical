# 用語解説記事の作成ルール

診療放射線技師向けの**用語解説記事**を、`src/content/articles/` に MDX で追加する手順書です。SEO・構造化データ・問題との相互リンクまで含め、公開品質を揃えます。

完成例: SEO と frontmatter は `src/content/articles/k-space.mdx`。本文の文体は `src/content/articles/t1-t2-weighted.mdx`（「縦磁化」から「T2 とは」までが基準）。

---

## 絶対に守ること

1. **公式・第三者の記事を転載しない。** オリジナルの解説だけを書く。
2. **用語解説の追加では、基本的なレイアウトと CSS を変更しない。** 通常は MDX（と、スキーマ拡張が必要なときだけ `src/content.config.ts`）だけ触る。記事ページの SEO は `src/pages/articles/[slug].astro` と `src/lib/article-seo.ts` が担う。
3. **記事 ID（ファイル名）と問題 JSON の `terms` を一致させる。** 例: `k-space.mdx` ↔ `"terms": ["k-space"]`。これで問題ページの「関連する用語」と記事ページの「関連する問題」が自動でつながる。
4. **FAQ は frontmatter の `faq` にだけ書く。** 本文 MDX に同内容の FAQ セクションを重複させない（表示・FAQPage 構造化データの単一ソース）。
5. **コミット・push は、ユーザーが依頼したときだけ。** ただし **Cursor の Cloud Agent**（Cursor Cloud / Background Agent）として割り当てブランチで作業するときは、コミット → push → PR 作成までが作業範囲（`.cursor/rules/cursor-cloud.mdc`）。Claude Code はこの例外に当たらない。どちらの場合も `main` へ直接 push しない。PR 本文は `.github/pull_request_template.md`。

## 1. ファイル名と ID

- 保存先: `src/content/articles/{term-id}.mdx`
- `{term-id}` は kebab-case・半角英数字とハイフン（例: `k-space`, `fat-suppression`）
- 対応する類似問題の `terms` 配列と**同じ文字列**にする
- `_template.mdx` は下書き用。公開記事の雛形にしない

## 2. frontmatter

```yaml
---
title: "MRIのk空間（k-space）とは｜意味・中心と周辺・国試の要点"
description: "MRIのk空間（k-space）とは、生データが並ぶ空間周波数ドメインです。…"
pubDate: 2026-08-21
draft: false
faq:
  - question: "k 空間とは何ですか？"
    answer: "MRI の k 空間（k-space）とは、**空間周波数**で…"
  - question: "k 空間の中心と周辺の違いは？"
    answer: "…"
---
```

| フィールド | ルール |
| --- | --- |
| `title` | SEO 用。**主キーワード +「とは」+「｜」+ サブトピック**。一覧・関連リンクの短い表示名は「｜」より前が使われる。任意の `termLabel` があれば、問題ページの「関連する用語」だけそちらを使う |
| `description` | 120〜160 文字目安。先頭に主キーワードと「とは」（または記事の主問い）。関連語を自然に含める。**国試向け**であることは差別化として入れてよい（「国試で問われやすい」など）。**特定の回次・問番号は書かない** |
| `pubDate` | 公開日 |
| `updatedDate` | 大幅更新時のみ（任意） |
| `draft` | 公開前は `true`。RSS・一覧・静的生成から除外される |
| `faq` | 2〜4 問。`answer` は Markdown 可（`**太字**` など）。構造化データ用にプレーンテキストも抽出される |

## 3. SEO キーワード設計

1 記事 = 1 テーマに集中する。

| 優先度 | 例（k 空間の場合） |
| --- | --- |
| Primary | `k空間`, `MRI k空間`, `k空間 とは` |
| Secondary | `k-space`, 関連概念（フーリエ変換、中心と周辺 など） |
| 差別化 | `国試`（回次・問番号は使わない）、初学者向けの落とし穴 |

**表記について**

- 本文では和文と英字の間に**半角スペース**を入れてよい（例: `k 空間`, `MRI 画像`）。読みやすさ優先。
- 検索の表記ゆれ（`k空間` / `k 空間`）は将来のサイト内検索で正規化する。**本文からスペースを消す必要はない。**

## 4. 本文構成

おおまかな流れ:

1. **冒頭** … 読者が講義でつまずく疑問から入る。定義の長文では始めない。回次・問番号は書かない
2. **見出し（H2）** … 用語をひとつずつ。意味、具体例、画像での見え方
3. **まとめ** … 短い文で、対比が残るように再整理する

`title` / `description` / FAQ はこれまで通り「とは」で始める。**本文の書き出しは別**で、下の文体に従う。

そのほか:

- 公式問題文・選択肢の転載はしない
- **記事は用語の解説であり、1 問の解説ページではない。** 「2026 年午前問 9 の要点」のように回次・問番号を title / description / 冒頭に入れない。国試で問われやすいポイント、という粒度は残す
- 公式 PDF へのリンクを本文に埋め込む必要はない。関連問題は末尾の自動一覧に任せる
- 製品情報など**参考用の外部リンク**を載せる場合は `target="_blank"` `rel="noopener noreferrer"` を付け、**`pnpm exam:external-links`** で台帳を再生成する（先例: `gadolinium.mdx`）

### 本文の文体

基準は `t1-t2-weighted.mdx` の「縦磁化」から「T2 とは」まで。高校生が講義で置いていかれた、という前提で書く。SEO 用の言い回しは title / description / FAQ に置き、本文には持ち込まない。

**冒頭**

- 読者の疑問を、かぎ括弧の箇条書きで 2〜4 個置く
- 「この記事では、上記のような疑問にお答えします。」
- 難しいと一言で認め、焦らなくていい、と短く言う
- 「ひとつずつ見ていきます。」
- 「○○とは、〜です。」で始めない。定義は見出しのあと

**文の長さと改行**

- 1文に事実は1つ。読点でつなげて長くしない
- 同じ話の続きや、ただし書きは `<br />` で次の行へ
- 話題が変わったら空行
- です・ます。である調にしない

**定義**

- 平たい言葉を先に、用語名はあと
- 「この、『平たい言い方』を『用語』と呼びます。」平たい言い方と用語の両方を太字にする
- 略語・英語は、最初の一度だけ括弧で添える。電波（RF パルス）、強い磁石の力（静磁場）
- 厳密な例外は1行で認めて、すぐ本筋に戻す。口語の一言で区切ってよい。発展的な説明は足さない

**具体例から見え方へ**

- 「例えば」で、対になる具体物を出す。水と脂肪、水と筋肉、のように読者が絵にできるもの
- 「だから」で、画像ではどう見えるかを書く
- その次の文で、長い・短い、暗い・明るいを言い切る
- 「組織」「戻りが遅いもの」のような抽象語より、水・脂肪・筋肉と書く
- 「見えやすい」でぼかさず、「見えます」と言い切る
- 同じ名詞を繰り返してよい。指示語で圧縮しない

**見出し**

- 「○○とは」「○○と○○」のように短くする
- 節の最初で、いま何を見るかを一言置く

型の例:

```mdx
例えば、「水」と「脂肪」の T1 は違います。

だから、**T1 強調画像では**、「水」と「脂肪」の見え方は違います。<br />
T1 強調画像では、「水」は暗く、「脂肪」は明るく見えます。

「水」の T1 は長く、「脂肪」の T1 は短いです。
```

### KeyPoint（フロー・数式・要点の囲み）

変換の流れ・関係式・読者に覚えてほしい一行など、本文中で**目立たせたい記述**には `<KeyPoint>` を使う。ライト/ダーク両方で読みやすい角丸の囲みになる。**MDX ファイルでの import は不要**（記事ページでグローバル登録済み）。

```mdx
<KeyPoint>
  k 空間（空間周波数） → 逆フーリエ変換 → 画像空間（位置ごとの信号）
</KeyPoint>
```

- **使う場面** … データの流れ、変換の向き、短い関係式、試験で押さえる一行
- **使わない場面** … 通常の段落、長い説明、プログラムコード（コードは ``` フェンス）
- 実装: `src/components/key-point.astro`

## 5. FAQ（frontmatter）

- 検索意図「〜とは」「〜の違いは」に答える質問を 2〜4 個
- 本文で触れた内容の**要約**に留め、本文と矛盾させない
- ページ上では `[slug].astro` が `faq` を「よくある質問」として描画
- `FAQPage` JSON-LD も同データから自動生成

---

## 6. 問題との相互リンク（自動）

| 方向 | 仕組み |
| --- | --- |
| 問題 → 記事 | 問題 JSON の `terms` に記事 ID を書く。問題ページの「関連する用語」は別タブで開く |
| 記事 → 問題 | 記事 ID と一致する `terms` を持つ公開問題を自動一覧（同じタブ） |

手動で URL を本文に書く必要はない。`terms` の整合だけ確認する。

---

## 7. 自動で付く SEO（実装済み・触らない）

記事ページ公開時に以下が出力される（`draft: false` のみ）:

- `og:type` = `article`
- `article:published_time` / `article:modified_time`
- JSON-LD: `Article`, `BreadcrumbList`, `FAQPage`（faq がある場合）
- canonical, sitemap, RSS

新記事追加だけなら **MDX を書くだけでよい**。

## 8. 公開前チェックリスト

- [ ] ファイル名 = 問題 `terms` の ID と一致
- [ ] `title` に主キーワードと「とは」（または主問い）、`description` に検索意図を反映。回次・問番号は入れない
- [ ] 本文は読者のつまずきから入り、「とは」の長文定義で始めない。1 問のための記事、という書き方をしない
- [ ] 1文が短く、続きは `<br />`、話題の切れ目は空行。定義は平たい言葉から用語名へ。例えば、のあとだから、で見え方を言い切る
- [ ] FAQ は frontmatter のみ（2 問以上推奨）
- [ ] `draft: false` にした
- [ ] 関連問題が記事末尾に表示される（`terms` 連携）
- [ ] 公式文の転載がない
- [ ] 参考用外部リンクを追加したとき **`pnpm exam:external-links`** で台帳を再生成した
- [ ] `pnpm run build` が通る

## 9. 新規作成の手順（エージェント向け）

ユーザーが用語解説記事の作成を依頼したら:

1. このファイルと、文体の基準 `t1-t2-weighted.mdx`（「縦磁化」から「T2 とは」）、SEO の基準 `k-space.mdx` を Read する
2. 対象用語とリンクさせる類似問題（`terms`）を確認する
3. `{term-id}.mdx` を SEO 方針に沿って作成する
4. 必要なら問題 JSON の `terms` に ID を追加する（未設定の場合）
5. ビルドでエラーがないか確認する
6. レイアウト・CSS・記事ページ実装は依頼がない限り変更しない
